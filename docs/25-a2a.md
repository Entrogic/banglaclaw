# 25 — Agent2Agent (A2A)

[A2A](https://a2a-protocol.org/) is an open protocol that lets agents built on different stacks (Google ADK, LangGraph, CrewAI, other BanglaClaw instances…) hand tasks to each other. MCP connects an agent to *tools*; A2A connects *agents to agents*. BanglaClaw implements both sides:

- the **server** on the gateway, so other agents can delegate Bangla, Banglish and English work to it ([ADR-0015](adr/0015-a2a-protocol.md));
- the **client** (`@entrogic-net/a2a`), so the BanglaClaw agent can call remote A2A agents as tools ([ADR-0016](adr/0016-a2a-client.md); see [Calling other agents](#calling-other-agents-client) below).

Both use the official [`@a2a-js/sdk`](https://www.npmjs.com/package/@a2a-js/sdk). The server speaks protocol **v1.0**, plus **v0.3** for older clients, over the **JSON-RPC** binding.

## Turning it on

```yaml
a2a:
  server:
    enabled: true
    publicUrl: https://bot.example.com   # optional; advertised in the agent card
    # description: "..."                 # optional; agent card description
```

`banglaclaw serve` then prints the card URL. Without `publicUrl` the card uses the origin of the request, which is wrong behind a reverse proxy, so set it in production.

## Endpoints

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/.well-known/agent-card.json` | none | The agent card. A request with `A2A-Version: 1.0` gets the v1.0 card; a request without the header gets the v0.3 card. Cached for 5 minutes, with an `ETag` and `Vary: A2A-Version`. |
| POST | `/a2a` | Bearer API key with the `run` scope | JSON-RPC 2.0. `A2A-Version: 1.0` selects v1.0 methods (`SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`); no header selects v0.3 (`message/send`, `message/stream`, `tasks/get`, `tasks/cancel`, `tasks/resubscribe`). |

The card lists:
- the JSON-RPC interface at `<publicUrl>/a2a` for both protocol versions;
- `streaming: true` and `pushNotifications: false`;
- one bearer security scheme;
- `text/plain` input and output;
- a general `chat` skill, followed by one skill per `SKILL.md` (its triggers become the tags).

## How a task runs

- **Auth and limits.** `/a2a` uses the same API keys, per-key rate limit and `X-RateLimit-*` headers as `/v1` (docs/18). A missing or invalid key gets HTTP `401`; a key without the `run` scope gets `403`. Each task takes one of the key's `maxConcurrentRuns` slots; when none is free the task ends `failed` with a message saying so.
- **Sessions.** Each A2A `contextId` maps to one session on the `a2a` channel, with `externalId` `<userId>/<contextId>`. Messages in the same context therefore share history, and two API users never share a context. The session's owner is the API user (`user:<id>`), so long-term memory and the workspace behave as they do for `/v1`. The workspace applies only if `a2a` is added to `workspace.channels`.
- **Input.** Text parts are used as they are, and data parts are added as JSON. File parts (`raw`, `url`) are rejected. A message longer than `gateway.maxInputChars` is rejected, and so is a `contextId` longer than 200 characters.
- **Events.** Every task emits:
  1. `task` (submitted);
  2. a `working` status whose metadata holds `sessionId`;
  3. the reply as one artifact named `response`;
  4. a final status whose metadata holds `sessionId`, `runId` and `language`.

  Tokens are not streamed as artifact chunks, because text written before a tool call may be replaced by the final answer.
- **Final states.**

  | Run status | A2A state |
  |---|---|
  | `completed` | `completed` |
  | `limited` | `completed`, with a note in the status message |
  | `error` | `failed` |
  | `aborted` by `CancelTask` | `canceled` |
| `aborted` by `runtime.timeoutMs` | `failed` ("Run timed out after …") |
  | `handoff` | `input-required` (a human operator has taken over) |

  Operator replies are not pushed to A2A callers. Poll the session with `/v1/sessions/:id/messages`, or follow it with `/v1/sessions/:id/events`.
- **Cancel.** `CancelTask` / `tasks/cancel` aborts a running task. It ends `canceled`, and the run is recorded as `aborted`.
- **Tasks vs. history.** Task objects are kept in memory per user (`GetTask` for another user's task returns "task not found"), so they disappear on restart. The conversation itself is stored in the session store like every other channel, and runs appear in the dashboard under the `a2a` channel.

## Example

```bash
curl -s https://bot.example.com/a2a \
  -H "Authorization: Bearer $BANGLACLAW_API_KEY" \
  -H "A2A-Version: 1.0" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"SendMessage","params":{"message":{"messageId":"m1","role":"ROLE_USER","contextId":"shop-42","parts":[{"text":"১৫০০ টাকার ১৫% ভ্যাট কত?"}]}}}'
```

The result is `{ "task": { "status": { "state": "TASK_STATE_COMPLETED" }, "artifacts": [{ "name": "response", "parts": [{ "text": "…" }] }], … } }`. With `SendStreamingMessage` the same events arrive as Server-Sent Events, one JSON-RPC response per `data:` line.

## Calling other agents (client)

Each entry under `a2a.agents` becomes one tool, `a2a__<name>`, that sends a message to a remote A2A agent and returns its reply:

```yaml
a2a:
  agents:
    weather:
      url: https://weather.example.com          # the card is fetched from <url><cardPath>
      # cardPath: /.well-known/agent-card.json  # the default
      headers: { Authorization: "Bearer ${WEATHER_AGENT_KEY}" }   # ${VAR} is read from the environment
      # description: "..."      # tool description for the model; default: the card's description and skills
      # timeoutMs: 120000       # per call, including waiting for the remote task
      # connectTimeoutMs: 15000 # for fetching the card
      # enabled: true
tools:
  allow: [a2a__weather]          # or a2a__* — remote agents are never allowed by default
```

`banglaclaw a2a list` fetches every card and shows the agent, its tool and whether the tool is allowed; `banglaclaw doctor` checks them too.

- **Connecting.** At startup BanglaClaw fetches each card (in parallel) and picks a transport from it: JSON-RPC or HTTP+JSON, protocol v1.0 or v0.3. An agent whose card cannot be fetched is reported as a warning (`unavailable`) and has no tool; it never stops BanglaClaw from starting. Cards are not re-fetched until the next start.
- **The tool.** Input is `{ message }`; output is `{ agent, reply, note?, truncated }`. Text and data parts are returned as text (data as JSON), and files as a short marker with their URL. Replies are capped at 20,000 characters. The tool's risk is `sensitive` (the message leaves this process), so it runs only when allowed in `tools.allow`, goes through the normal validation, timeout and audit path, and is visible in `tool list`.
- **Conversations.** Each BanglaClaw session gets its own remote conversation: the first call starts one, and later calls from the same session send the `contextId` the remote agent returned, so it keeps context. The mapping is kept in memory (bounded), so after a restart the next call starts a new remote conversation.
- **Waiting.** The message is sent as a blocking `SendMessage`. If the agent answers before the task is finished, BanglaClaw polls `GetTask` until it is, within `timeoutMs`; when the run is cancelled or times out, it sends `CancelTask`.
- **Failures.** `failed`, `rejected`, `canceled` and `auth-required` tasks, HTTP and JSON-RPC errors all come back to the model as a tool error observation, never as an exception in the run.
- **Credentials.** `headers` are sent only to the origin of `url`. If a card points its interface at another host, requests there go without them, so a compromised or mistaken card cannot collect the key.
- **Trust.** The remote reply and the card text are untrusted input to the model, like MCP output. Set `description` to keep the card's wording out of the prompt, and allow only agents you trust.
- **Paused for now:** tasks that end in `input-required` (the remote agent asks a question, or a human operator took over, as BanglaClaw's own server does on handoff) are returned as a tool error with the agent's question; continuing such a task is not supported yet.

The server and client are independent: `a2a.server.enabled` is not needed to call other agents. An MCP server cannot be named `a2a`, because that prefix belongs to these tools.

## Not supported (yet)

- Push notifications (webhooks) and the authenticated extended card.
- The HTTP+JSON (REST) and gRPC bindings on the server.
- File input and output.
- Client: continuing `input-required` tasks, streaming partial replies, and OAuth or other non-header auth schemes.
